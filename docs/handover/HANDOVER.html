1. 개요와 현재 상태

Personal AI OS는 한 사람(소유자)을 위한 개인용 AI 시스템이다. 모든 구성요소는 Windows PC의 Docker Desktop(WSL2) 위에서 컨테이너로 실행되고, 외부로 열린 포트 없이 127.0.0.1에만 바인딩된다.

  • 대화 창구: Hermes Agent(오픈소스 에이전트, Gemini 모델). Telegram 등에서 소유자의 요청을 받아 작업을 위임하는 관리자 역할만 한다. 직접 코딩하거나 셸을 쓰지 않는다.
  • 작업 실행: Claude Code Worker와 Codex Worker가 Controller에서 작업을 가져가 격리된 Git worktree에서 코드를 수정하고 커밋한다.
  • 검토·승인: 소유자가 Admin Dashboard에서 diff를 보고 커밋을 승인·거부한다.
  • 게시 준비: Test Runner가 승인 대상 커밋에 대해 테스트를 실제로 실행하고, GitHub Publisher가 Git 객체·테스트 증거·별도 게시 승인을 독립 검증한다. 실제 GitHub Push/PR은 현재 비활성이다.
  • 학습: AI Learning OS(L1) — 학습 분야·아이디어·목표·버전이 있는 학습 로드맵·AI 초안(소유자 승인 필수).

반드시 지켜야 할 정책

  • POLICY A — 테스트 필수: 승인 대상 커밋에 대해 Test Runner가 실행·서명한 통과 기록이 없으면 게시 불가. Publisher는 설정값이 PUBLISHER_REQUIRE_REPORTED_TESTS=true가 아니면 시작하지 않는다.
  • POLICY B — Worker Author 보존: 승인된 커밋 SHA를 그대로 게시. author/committer/메시지 재작성 금지. PUBLISHER_COMMIT_AUTHOR_POLICY=preserve_worker 고정.
  • 승인 분리: 코드 리뷰 승인 ≠ 게시 승인 ≠ 게시 요청. 각각 별도 확인 단계와 CSRF 검사.
  • 실제 GitHub Push/PR/Merge는 현재 비활성(Controller CONTROLLER_PUBLISH_ENABLED=false, Publisher PUBLISHER_PUBLISH_BACKEND=disabled).
  • AI 출력은 제안일 뿐: Learning 로드맵은 소유자가 차이를 보고 승인해야 바뀐다. 사용자 고정 Deadline은 AI가 바꾸지 않는다.
  • 비밀 값은 로그·응답·커밋에 남기지 않는다. 모든 포트는 127.0.0.1. Docker 소켓 마운트 금지.

4.1 Hermes와 통합 (services/hermes-integration)

Hermes는 외부 프로젝트(nousresearch/hermes-agent:stable)이며 설정·데이터는 data/hermes/(bind mount)에 있다. 기본 모델은 Gemini(gemini-3.5-flash-lite), 키는 secrets/hermes.env.

  • 플러그인 personal_ai_task (plugins/personal-ai-controller/): 동작 submit, status, result, wait, list, cancel, projects, system_status, review. broker URL과 클라이언트 키 파일만 사용한다.
  • Skill: skills/personal-ai-controller/SKILL.md — 언제 어떻게 작업을 위임하는지.
  • SOUL 규칙: hermes-config/SOUL.personal-ai.md — 관리자 역할, 승인 요청 거절 등.
  • toolset 축소: telegram/cli/cron 플랫폼에서 terminal, code_execution, file, computer_use, delegation 제거. scripts/configure-hermes.mjs가 적용하고, 원본은 data/hermes/backups/에 보관.
  • pre_tool_call guard(guard.py): browser 도구의 file:·내부 서비스 접근 차단(패턴 기반 보조 수단).
  • 참고: Hermes에는 자체 memory(에이전트 메모/사용자 프로필)와 kanban 기능이 있다. 이는 Hermes 내부 기능이며 Personal AI의 지식 그래프가 아니다. 학습 데이터의 원본은 Learning DB다.

4.2 hermes-broker (services/hermes-broker)

Hermes가 Controller 토큰을 갖지 않도록 하는 자격 증명 중계기. 호출자는 X-Broker-Key를 보내야 하며(없으면 401), 허용 경로만 Controller로 전달한다: GET /system/status, /projects, /projects/:id, /tasks, /tasks/:id, /tasks/:id/diff, /tasks/:id/review, POST /tasks, /tasks/:id/cancel. 작업 생성은 분/시간당 제한이 있다. 그 외(approve, publication 등)는 404.

4.3 Controller (services/controller)

NestJS 12 + better-sqlite3. 단일 진실 공급원(작업·프로젝트·리뷰·테스트·게시). DB는 controller-data 볼륨의 /var/lib/controller/controller.db(WAL, synchronous=FULL).

역할(토큰 → principal)

admin(name=admin 운영자 / name=dashboard), worker(claude/codex), delegator(hermes), publisher, test-runner. 토큰은 secrets/controller.env에서 읽고 메모리에는 SHA-256 digest만 둔다. 모든 핸들러는 기본적으로 admin을 요구하며 @RequireRole로 완화한다.

스키마 (마이그레이션 v1–v6)

버전테이블핵심
v1–v2tasks상태 queued → running → completed/failed, cancel_requested → canceled. lease·heartbeat, created_by, idempotency key
v3projectslocal/github, 허용 에이전트, enabled, allowCodeChanges, 동기화 상태, cachedHeadSha. v6에서 test_commands 추가
v4reviews(task, head SHA)당 1행. awaiting_approval → approved/rejected, invalidated. 조건부 UPDATE로 원자적 결정
v5publicationsdry-run/publish 요청. 리뷰당 진행 중 1개, 게시 1회(unique index)
v6test_validations, publish_authorizations테스트 실행 기록(서명된 증거), 별도 게시 승인(30분 만료, 1회용, 멱등 키)

모듈

Tasks, Workers(내부 API), Projects(+GitHub client), Reviews, TestValidations, Publications, Health. 리뷰 diff는 Worker 보고서의 diff가 해당 커밋을 정확히 설명할 때만 신뢰한다. Private 프로젝트의 patch는 delegator(Hermes)에게 주지 않는다.

4.4 Claude / Codex Worker (services/worker)

  • 폴링(5초)으로 자기 에이전트 작업을 claim → 작업 공간 준비 → CLI 실행(heartbeat, 타임아웃 30분) → 커밋 → 결과 보고.
  • 작업 공간(workspaces/<agent> bind mount): local 프로젝트(sandbox), GitHub 프로젝트는 export 볼륨(/repo-cache, 읽기 전용)에서 만든 자체 bare clone repos/<id>.git, 작업마다 worktree .worktrees/<taskId>, 브랜치 <agent>/task-<taskId>.
  • 신뢰하지 않는 저장소 설정: hooks 비활성, symlink를 일반 파일로, fsck, 서브모듈 미초기화, file 프로토콜만.
  • 커밋 후 diff 기록(파일별 ±, 바이너리/민감 파일 표시, 200KB 이하 patch)과 GitHub 프로젝트는 git bundle + manifest를 /artifacts(owner-only 0700)에 기록 → Test Runner·Publisher가 읽음. 이전 작업은 export-artifact CLI로 생성.
  • 로그인 정보: data/claude-home, data/codex-home(구독 로그인, API 키 과금 아님). Codex는 bubblewrap용 seccomp 프로필(images/coding-worker/seccomp/)을 사용 — 임의로 완화하지 말 것.

4.5 repo-sync (services/repo-sync)

평소에는 실행되지 않는 도구 컨테이너(profiles: tools). sync: GitHub 저장소를 repo-cache에 bare 미러로 가져옴(체크아웃 없음, 크기 제한 2GiB/전체 20GiB/파일 100MB, Private는 PAT extraHeader). export: 에이전트별(repo-export-claude/-codex) 및 publisher용(repo-export-publisher) 볼륨에 허용된 프로젝트만 독립 복사본으로 둔다. 권한을 회수하면 export에서 사라진다. 실행은 sync-project.ps1, provision-exports.ps1.

4.6 Admin Dashboard (services/dashboard)

  • BFF: 브라우저는 Dashboard 서버와만 통신. 서버가 Controller/Learning을 토큰으로 호출(src/lib/controller.ts, src/lib/learning.ts, server-only).
  • 인증: 단일 관리자(owner), scrypt 해시(secrets/dashboard-admin.hash). 서버 메모리 세션(유휴 30분, 최대 8시간), HttpOnly+SameSite=Strict 쿠키.
  • CSRF: 세션별 토큰 + Origin/Sec-Fetch-Site 검사. Referrer-Policy: same-origin(no-referrer는 Origin: null 문제를 일으켰음). 실패 시 원래 화면으로 돌아가 메시지 표시.
  • 로그인 제한: IP·사용자별 15분 5회. 서명된 장치 쿠키로 로컬 공격자가 소유자를 잠그지 못하게 함. server-entry.cjs가 TCP peer로 클라이언트 IP를 결정(위조된 X-Forwarded-For 무시, DASHBOARD_TRUSTED_PROXIES만 예외).
  • 화면: Overview, Tasks, Projects, Code Reviews(+Publishing 패널), Learning(Overview/Ideas/Roadmap Explorer). 메뉴는 src/modules/registry.ts의 정적 배열(런타임 플러그인 아님).
  • 보안 헤더: CSP, X-Frame-Options DENY, nosniff, no-store. diff·사용자 입력은 React 텍스트로만 렌더링.

4.7 Test Runner (services/test-runner)

  • Controller의 test_validations를 claim → Worker bundle과 publisher export로 정확한 커밋을 checkout(검증 후 객체 복사, alternates 제거) → 프로젝트에 관리자가 등록한 testCommands를 실행.
  • 오케스트레이터는 root지만 capability는 CHOWN, SETUID, SETGID, KILL, DAC_READ_SEARCH만. 테스트는 uid 10001, 깨끗한 환경 변수(BASE_SHA, HEAD_SHA 등만), test-internal 네트워크(인터넷 없음). 남은 프로세스는 종료.
  • 결과(종료 코드·시간·출력 hash)를 evidence JSON으로 만들고 HMAC-SHA256으로 서명. Controller는 키가 없고 상태를 다시 계산해 "passed"를 함부로 올리지 못함.

4.9 Learning Service (services/learning, L1)

  • NestJS + SQLite(learning-data 볼륨, 스키마 v1): domains(6 상태, 계층, 보관만), ideas(Inbox, 자동 일정 편성 없음), goals(사용자 고정 Deadline), roadmaps / roadmap_versions(불변) / roadmap_nodes / prerequisite_edges(DAG) / skills(공유, canonical 이름) / ai_proposals / ai_calls(비용) / audit_events.
  • 모든 변경은 제안 → 승인: 수동 편집, AI 초안, 복원, 가져오기. 적용은 base version 조건부 UPDATE(충돌 409 VERSION_CONFLICT). 순환 422 PREREQUISITE_CYCLE(경로 포함). 복원은 새 버전.
  • AI Provider(src/provider/provider.ts): Gemini REST, JSON schema 출력 + 서버 재검증, 월 상한(호출 전 최악 비용 검사), 타임아웃·재시도 1회, 호출/비용 기록. 설정 전에는 PROVIDER_NOT_CONFIGURED. 키는 헤더로만.
  • JSON export/import(빈 DB에만, 버전 hash 재검증), 백업/복원 스크립트(볼륨 밖 data/backups/learning/, 최근 14개).
  • 네트워크: learning-internal(Dashboard만), learning-egress(AI 제공자용). Hermes 연동은 L4 예정.

5. 핵심 흐름

5.1 코딩 작업 → 리뷰 → 게시 준비

  1. 소유자가 Telegram으로 Hermes에 요청 → Hermes가 personal_ai_task submit → broker → Controller POST /tasks(프로젝트·에이전트 지정).
  2. 해당 Worker가 claim → worktree에서 CLI 실행 → 커밋 → diff·bundle 기록 → complete.
  3. Controller가 리뷰(awaiting_approval)를 만들고, 프로젝트에 테스트 명령이 있으면 테스트 실행을 자동 요청.
  4. Test Runner가 실행·서명 → 결과 저장.
  5. 소유자가 Dashboard Code Review에서 diff 확인 → Approve commit(체크박스 확인).
  6. Publishing 패널에서 Validate / Dry-run → Publisher가 12단계 검사 → eligible.
  7. Authorize publishing…(별도 확인) → 게시 승인(30분) → Dry-run 다시 실행 시 canPublish=true.
  8. Publish는 현재 비활성(PUBLISH_DISABLED). 활성화 시 Publisher가 승인된 커밋을 그대로 personal-ai/<task> 브랜치로 push하고 draft PR을 만든다(E-2B 이후 단계).

5.2 학습 로드맵

  1. Learning Overview에서 분야 → 목표(주간 시간, Deadline) → 로드맵 생성.
  2. Explorer에서 수동 편집(JSON) 또는 AI 초안 → 제안 저장(검증 실패 시 invalid).
  3. 차이 확인 → 체크박스 → 승인 → 새 버전. 이전 버전 복원은 새 버전으로.
